# Стартовый промпт для Claude Code

Скопировать целиком в начало новой сессии Claude Code, находясь в папке `agent-kit`.

---

Ты продолжаешь проект «защищённый AI-ассистент руководителя» для конкурса. Читай `SPEC.md` — там требования заказчика дословно. Каркас уже есть и проходит 24 проверки: `npm test`.

## Что уже работает, не ломай

- `src/types.ts` — роли одной строкой, `Actor`, `Doc`, `Chunk`, `QueueItem`, `TrailEntry`
- `src/access.ts` — фильтр прав **до** поиска, поиск по целым словам, `assertNoLeak`
- `src/injection.ts` — сканер команд в документах, обёртка маркерами, `SYSTEM_PROMPT`
- `src/model.ts` — единая точка `ask()`: живой API, при недоступности тихо падает на заготовки
- `src/load.ts` — документ сканируется при загрузке, метка `tainted` наследуется всеми кусками
- `tests/evals.ts` — 24 проверки

Правило: любая новая функция, которая читает данные, ходит через `visibleDocs`/`search`, а не мимо.

## Что добавить, в этом порядке

### 1. Безопасный повтор (требование ТЗ, проверяется на демо)
`src/once.ts`: `createOnce(key, factory)`. Ключ = sha256(id источника + нормализованное содержание). Если ключ уже в журнале — вернуть существующий объект и запись «повтор», новый не создавать. Применить ко всем созданиям: задача, письмо, встреча.
Проверка в эвалах: два одинаковых запроса подряд → одна задача, две записи в журнале.

### 2. Протокол встречи
`src/protocol.ts`: вход — расшифровка с таймкодами, выход — объект с полями `решения`, `риски`, `вопросы`. Каждый пункт несёт `timecode` и короткую цитату из расшифровки. Если в расшифровке нет данных для поля — строка «требует уточнения», не выдумывать.

### 3. Задачи из протокола
`src/tasks.ts`: из каждого решения протокола — черновик задачи с полями `владелец`, `срок`, `основание` (ссылка на пункт протокола). Задача без основания не создаётся — кидать ошибку. Все черновики идут в очередь подтверждения, ни одна не создаётся сама.

### 4. Управленческий обзор
`src/overview.ts`: собрать по реестру задач — что закрыто, что просрочено, что без исполнителя, из каких встреч пришло. Из каждой строки обзора должна быть ссылка обратно на задачу и дальше на пункт протокола. Это критерий приёмки: протокол ↔ задачи ↔ обзор.

### 5. Поиск по документам с доказательством
`src/find.ts`: на запрос возвращать список находок, каждая — `{файл, строка, цитата, почему подходит}`. Пусто — так и сказать. Никаких обобщений без ссылки.

## Чего не делать

- Не ставить базу данных и векторный поиск. Для демо хватит файлов и поиска по словам.
- Не подключать живую почту и живой Telegram. ТЗ разрешает mock-сервисы — сделать их, с описанным успехом **и** ошибкой.
- Не давать агенту ничего отправлять наружу. Любой исход — в очередь подтверждения.
- Не добавлять зависимостей без необходимости. Node 22 и `--experimental-strip-types`, без сборщика.

## Как проверять себя

После каждого шага: `npm test`. Проверки не проходят — чинить, прежде чем идти дальше. Добавлять новую проверку на каждое новое требование, а не только код.

Отдельно убедиться, что демо-атака ловится: в `data/documents/04-pismo-postavshika.md` спрятана команда. Агент обязан её показать как «скрытую команду», а не выполнить.

### 6. Битрикс24 — только режим заглушки

`src/bitrix.ts`, функция настоящей формы:

```ts
createTask({ title, responsibleId, deadline, description }): Promise<{ id: number }>
```

Внутри — **локальная заглушка, никаких сетевых вызовов**. Возвращает такой же ответ, какой вернул бы портал: `{ result: { task: { id } } }`. Режим переключается в `.env`:

```
BITRIX_MODE=mock   # mock | live
BITRIX_WEBHOOK=    # пусто в режиме mock
```

В режиме `live` тот же модуль пойдёт на `tasks.task.add` через входящий вебхук — но этот путь сейчас не нужен и не тестируется. Важно только, чтобы сигнатура и форма ответа совпадали, тогда переключение не потребует переписывания.

Заглушка обязана уметь три исхода, они нужны для демонстрации требований ТЗ:

1. успех — задача создана, возвращён id;
2. ошибка `503` — задача не потеряна, остаётся в очереди со статусом «ждёт», повтор автоматический;
3. повтор — тот же `ключПовтора` возвращает существующую задачу, вторая не создаётся.

Исполнитель в Битриксе задаётся числовым `RESPONSIBLE_ID`, а не именем. Соответствие «имя → id» держать в `data/people.json`.

Проверка в эвалах: два вызова `createTask` с одним ключом → одна задача, две записи в журнале.
