# Защита: соответствие слайдам «Безопасная разработка с ИИ»

Проверено по коду и тестам (`npm test`, 458 проверок). «Где видно» — что показать на защите.

## Модель угроз (слайд 6)

| Угроза со слайда | Что у нас | Где видно |
|---|---|---|
| Внешний атакующий прячет инструкции в документах | Поиск скрытых команд при загрузке и в найденных кусках; документы в модель идут в рамке «это данные»; команда не выполняется | «Решения» → «Защита», письмо поставщика |
| Инсайдер использует агента для обхода контролей | Агент работает только с правами того, кто спрашивает; закрытое неотличимо от несуществующего (404, без названий) | Войти менеджером: закрытых документов нет нигде |
| Скомпрометированный инструмент действует с правами пользователя | Внешних инструментов, MCP и навыков нет; наружу ходит только модель | Тест «сеть: единственный вызов — модель» |
| Защищать код, секреты, инфраструктуру, данные клиентов | Права по ролям, DLP, журнал | вкладки «Маршрут», «След действий» |

## Шесть принципов (слайд 13)

1. **Вывод ИИ недоверенный.** Цитаты и номера сегментов протокола проверяет код, а не модель. Всё, что написала модель, выводится как текст, не как разметка (в интерфейсе нет `innerHTML`). Задачи и письма из вывода уходят только после подтверждения человеком.
2. **Наименьшие привилегии.** Роли и подразделения; каждый запрос идёт через «кто спрашивает». Менеджер подтверждать не может (403). Автопостановка задач выключена по умолчанию.
3. **Изоляция контекста.** Загруженные файлы и файлы с ноутбука видны только загрузившему. Документы в модель идут в рамке с запретом выполнять команды.
4. **Проверка зависимостей.** В проекте один пакет (`tsx`), список закрыт тестом, есть `package-lock.json` с зафиксированными версиями. Придуманных (slopsquatting) пакетов нет.
5. **Секреты вне промптов.** Новый модуль DLP: ключи API, токены, пароли, закрытые ключи, строки `.env` и номера карт (по Luhn) заменяются на «[скрыто]» в запросе, в журнале и перед отправкой в модель. Файлы `.env`, `id_rsa`, `*.pem`, `*.key` и файлы с секретами не принимаются при загрузке и из папки ноутбука. Ключ модели только в `.env`, а `.env` в `.gitignore`.
6. **Многослойная защита.** Права, поиск скрытых команд, DLP, подтверждение человеком, идемпотентность, журнал. Любой один слой можно обойти, цепочка из пяти: нет.

## План реагирования (слайд 9 и 14)

1. Подозрение на утечку ключа: отозвать ключ у провайдера, заменить в `.env`.
2. Открыть «След действий», отфильтровать «только отказы агента»: там записи «секрет скрыт», «файл отклонён», «найдена скрытая команда».
3. Убедиться по журналу, что наружу ничего не уходило: письма и приглашения в журнале только после действия человека.
4. Файл с командой убрать из документов, источник проверить.

## Что не закрыто (честно)

- Список признаков скрытых команд в `src/injection.ts` короткий (десять шаблонов). Не покрыты английские варианты вроде «disregard the above», команды `curl … | sh`, «загрузи и запусти скрипт», просьбы прочитать `.env`. Файл защищённый: правки только с вашего слова.
- Срок действия пересылки (7 дней) записан как правило, в демо не реализован: настоящих внешних подключений нет, пересылку можно отозвать вручную.
- Отдельного сканера кода (SAST/SCA) нет, потому что демо не генерирует код.

## Gmail и Telegram: как показать и защитить

- В демо это имитации по ТЗ (слайд 09): письмо поставщика лежит в папке документов, сообщения Telegram только пишутся в журнал. Вкладка «Настройки» показывает оба подключения со статусом «имитация».
- Защита строится на трёх частях опасной связки (SPEC.md, раздел «Почта и мессенджеры»): доступ к личным данным, чтение чужого текста, отправка наружу. Вместе их не даём: письма читаются только на чтение, отправляет всегда человек.
- Что показать на защите: письмо с командой «забудь инструкции» попадает в «Решения → Защита», а ответ на него ждёт кнопки «Отправить ответ»; в журнале видно, что до нажатия ничего не ушло.
- Права в боевой версии: Gmail только `gmail.readonly` и `gmail.compose` (черновики), Telegram через Bot API видит только сообщения, адресованные боту.
