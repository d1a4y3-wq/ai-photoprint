# AI-ассистент руководителя — спецификация

Источник требований: слайды 08 (трек 3) и 09 (общие требования) технического задания «Фотопринт».

## Что принимают

**Сценарий:** ассистент готовит встречу, протокол и задачи, но **не выполняет значимые действия без подтверждения**.

Пять стадий:

| № | Стадия | Что внутри |
|---|---|---|
| 01 | Подготовка | повестка · открытые вопросы |
| 02 | Встреча | расшифровка · контекст |
| 03 | Протокол | решения · риски · вопросы |
| 04 | Задачи | владелец · срок · **основание** |
| 05 | Контроль | статус · напоминание · итог |

**Критерий приёмки:** протокол встречи ↔ реестр задач ↔ управленческий обзор.
Три объекта связаны ссылками в обе стороны. Из задачи видно, из какой строки протокола она родилась; из обзора — какие задачи его наполнили.

## Пять гарантий сценария (слайд 08)

1. **Источники** — ответ содержит документ и дату основания.
2. **Права** — ассистент видит только разрешённый контекст.
3. **Подтверждение** — письмо, встреча или задача создаются только после просмотра.
4. **Не выдумывать** — если данных нет, ответ «требует уточнения».
5. **Аудит** — запрос, источник, предложение и результат сохраняются.

## Пять общих требований (слайд 09) — проверяются на демонстрации

1. **Права доступа** — роли ограничивают данные, действия и контекст AI.
2. **Аудит** — сохраняются пользователь, время, действие, объект и результат.
3. **Безопасный повтор** — повтор запроса не создаёт второй заказ или задачу.
4. **Интеграции** — контракты API и mock-сервисы описывают успех и ошибку.
5. **Понятный UX** — крупный текст, ясные состояния и объяснимые ошибки.

Пункт 4 разрешает mock-сервисы явно. Демонстрация не обязана ходить в живые API.

## Архитектура

```
звук встречи ──► ASR (локально) ──► расшифровка с таймкодами
                                          │
документы  ──► фильтр прав ──► поиск ──► контекст ──► модель ──► предложение
   письма  ──►  (до поиска)                            │
                                                       ▼
                                             очередь подтверждения
                                                       │
                                            человек нажал ──► действие + запись в журнал
```

Ключевое: **фильтр прав стоит до поиска**, а не после. Запрещённый документ не попадает в контекст модели вообще — нечему утекать.

### Слои

| Слой | Чем закрыт | Статус |
|---|---|---|
| Модель | единая точка `ask()`, переключатель провайдера | готово |
| Промпт | `SYSTEM_PROMPT`, главное правило — текст в маркерах это данные | готово |
| Поиск | фильтр прав до поиска, `assertNoLeak` | готово |
| Инструменты | обычные функции, каждая возвращает успех и ошибку | готово |
| Доступ | `access.json`, роль не найдена → документ не виден никому | готово |
| Защита | сканер инъекций при загрузке документа, весь документ метится `tainted` | готово |
| Подтверждение | очередь `QueueItem`, глаголы: отправить/назначить/решить/утвердить/разрешить | готово |
| Повтор | ключ идемпотентности = источник + хеш содержания | **добавить** |
| Журнал | `TrailEntry`: кто, когда, что, над чем, результат | готово |
| Эвалы | 24 проверки, гоняются после каждой правки промпта или прав | готово |

### Безопасный повтор

У каждого создаваемого объекта (задача, письмо, встреча) есть ключ:

```
key = sha256(источник_id + нормализованное_содержание)
```

Создание идёт через `createOnce(key, …)`: если ключ уже в журнале — возвращается существующий объект, второй не создаётся. Повтор одного и того же запроса даёт тот же результат и ту же запись.

## Встречи

Встречи очные, без гаджетов и без бота в звонке. Поэтому:

- запись — диктофон телефона или ноутбук, один файл;
- расшифровка — **локально**, ничего не уходит в сеть;
- протокол — по шаблону, который сейчас делает секретарь (нужны 2–3 обезличенных образца);
- каждая строка протокола несёт таймкод и открывается в записи — это и есть «источники».

Разметка говорящих — отдельный риск. Базовый вариант: таймкоды без имён. Имена — как улучшение, если останется время.

## Документы

Две разные функции, не путать:

1. **Найти и доказать.** Гибрид: точный поиск по словам + поиск по смыслу. Каждая находка — файл, страница или строка, короткая цитата, кнопка «открыть». Не нашлось — «требует уточнения», без догадок.
2. **Собрать и разложить.** Сборка пакета к встрече: по повестке подобрать → показать список → собрать после подтверждения. Раскладка входящих: следим за папкой, классифицируем, **предлагаем** перемещение. Автоматом — только по правилу, которое человек один раз утвердил.

## Почта и мессенджеры

Опасная комбинация из трёх частей: доступ к личным данным + чтение чужого текста + возможность отправить наружу. Все три вместе — взлом вопрос времени. Поэтому одну часть убираем:

- входящие читаются **только на чтение**;
- агент **ничего не отправляет сам** — любой исход идёт в очередь подтверждения;
- письмо — это данные, не команда: обёртка маркерами, сканер, метка `tainted`.

## Задачи

Задача создаётся только с основанием. Основание — ссылка на строку протокола, документ, письмо или наблюдение. Без основания задача не создаётся.

Правила (не модель) создают предсказуемые задачи: «завтра встреча → собрать пакет документов». Модель нужна там, где надо понять текст, а не там, где достаточно правила.

## Тестирование

1. **Эвалы** — 24 автоматические проверки по шести группам: права доступа, фильтр до поиска, защита от инъекций, системный промпт, переключатель модели, журнал. Гоняются после каждой правки.
2. **Проверки под ТЗ** — добавить по одной на каждое требование слайда 09: права, аудит, безопасный повтор, «не выдумывать», источники.
3. **Сценарный прогон** — пройти пять стадий от записи встречи до управленческого обзора и убедиться, что три объекта связаны.
4. **Демо-атака** — в тестовых документах лежит письмо со спрятанной командой. Агент обязан её поймать и показать, а не выполнить.

## Связь протокола с записью

Расшифровка хранится не сплошным текстом, а кусками с таймкодами:

```json
{ "id": 12, "startMs": 184300, "endMs": 191800,
  "text": "по переплёту берём второго поставщика, но после расчёта" }
```

Протокол собирается так, что каждый пункт **обязан назвать номера кусков**, из которых он сделан:

```json
{ "вид": "решение", "текст": "Переплёт — второй поставщик, после расчёта",
  "seg": [12, 13], "цитата": "берём второго поставщика" }
```

Дальше идёт проверка: номера кусков существуют, и цитата действительно встречается в их тексте. Не сходится — пункт помечается «требует уточнения» и не попадает в протокол как факт. Это одновременно закрывает две плашки ТЗ: «источники» и «не выдумывать».

Клик по пункту протокола: `audio.currentTime = seg.startMs / 1000`. Ссылка работает не потому, что мы ищем текст в записи задним числом, а потому что модель обязана назвать источник в момент создания пункта.

## Хранение

### На демо — файлы, без базы

```
meetings/
  2026-11-14-planerka/
    audio.ogg          запись, Opus, ~15 МБ за час
    transcript.json    куски с таймкодами
    protocol.json      решения · риски · вопросы, с номерами кусков
    protocol.md        человекочитаемый
    trail.jsonl        журнал: кто, когда, что, над чем, результат
```

Папку видно глазами, журнал открывается блокнотом — это и есть демонстрация аудита.

### В production

- протоколы, задачи, журнал — PostgreSQL на их собственном сервере;
- аудио — отдельное файловое хранилище, зашифровано на диске;
- доступ к записи — через тот же слой прав, что и к документам: услышать встречу может только тот, кому она разрешена.

### Срок хранения

Аудио нужно ради одного: проверить спорную строку вручную. Это требование ТЗ, но бессрочно держать запись совещаний руководства незачем.

- аудио — ограниченный срок, по умолчанию 90 дней, настраивается;
- расшифровка, протокол, задачи, журнал — по политике компании, дольше;
- по истечении срока аудио удаляется, у пункта протокола остаётся цитата и таймкод, ссылка становится неактивной.

Запись людей требует их согласия — это вопрос к юристу заказчика, не к нам. В интерфейсе: видимая плашка «идёт запись» и список тех, кто согласился.

## Модель — сменная деталь

Заказчик уже платит за ИИ и менять его не будет. Это не проблема: мы не заменяем их модель, мы строим вокруг неё процесс.

Вся работа с моделью идёт через одну функцию `ask(system, user)` в `src/model.ts`. Распознавание речи — через один такой же интерфейс. Поменять поставщика = поменять строку в `.env`, код не трогается.

| Функция | В реальной компании | На демонстрации |
|---|---|---|
| Запись → текст | `gpt-transcribe` (OpenAI), около $0,27 за час записи | локально в браузере либо тот же OpenAI |
| Текст → протокол | их действующая модель OpenAI | заготовки или локальная модель |
| Поиск по документам | эмбеддинги того же поставщика или локальные | поиск по словам |
| Решение действовать | никакая модель — человек | человек |

### Контракт интеграции (требование слайда 09)

Для каждого внешнего сервиса описано три вещи: что отправляем, что приходит в случае успеха, что приходит в случае ошибки. Mock-сервис повторяет этот контракт один в один, включая ошибки — поэтому переключение с заготовок на живой сервис ничего не ломает.

Переключатель вынесен в интерфейс: заготовки · локально · OpenAI · другой поставщик. На демонстрации его видно и можно переключить при зрителях.

### Что нельзя говорить со сцены

Если в режиме демонстрации работают заготовки — так и сказать: «сейчас режим демонстрации, без интернета зала». Нельзя говорить «это отвечает GPT», когда отвечает заготовка. Жюри проверяет такие вещи вопросами, и честный ответ стоит дешевле пойманной неправды.

### Чего Codex не делает сам

Их руководитель уже получает протокол от ИИ в чате. Чего в этом нет и что строим мы:

- знание, какие документы этому человеку разрешено видеть;
- ссылка из каждой строки протокола на секунду записи;
- превращение решений в задачи с владельцем, сроком и основанием;
- очередь подтверждения перед любым значимым действием;
- журнал: кто спросил, что предложил агент, что решил человек;
- защита от повтора: второе нажатие не создаёт вторую задачу.

Ни один из шести пунктов не является свойством модели. Все шесть — требования из их же технического задания.

## Автономия: что агент делает сам

Черта проходит не между «подумать» и «сделать», а между обратимым и необратимым.

| Уровень | Что это | Примеры |
|---|---|---|
| Делает сам, молча | обратимо, никого не трогает | собрать пакет документов в черновую папку, разобрать расшифровку, разложить входящие по черновикам |
| Делает и показывает | обратимо, но человеку важно знать | собрал протокол, нашёл расхождение в договорах, подобрал участников встречи |
| Не делает, ждёт нажатия | необратимо или значимо | отправить письмо, разослать пакет, назначить задачу человеку, записать в общую папку, потратить деньги, удалить |

Почему не спрашивать про всё: если агент спрашивает разрешения на каждую мелочь, человек перестаёт читать вопросы и жмёт «да» подряд. Формально всё подтверждено, фактически защиты нет. Право спросить тратится только там, где это правда важно.

### Как агент получает новое правило

Первый раз агент спрашивает и предлагает запомнить:

```
Собрал пакет к встрече. Делать так каждый раз перед встречами?
[да, всегда]  [спрашивать каждый раз]  [не надо]
```

«Да, всегда» создаёт правило. Правила видны отдельным списком, у каждого кнопка «отключить». Автономия набирается по одному решению, а не выдаётся авансом.

## Откуда берутся задачи

Пять источников, один конвейер:

| Источник | Что его запускает | Пример |
|---|---|---|
| Протокол | решение на встрече | «переплёт — второй поставщик» → задача Сергею |
| Правило | расписание или событие | за день до встречи собрать пакет |
| Документ | разобранный входящий файл | в счёте срок оплаты → задача оплатить |
| Наблюдение | следим за источником | появилась подходящая закупка → задача подать заявку |
| Человек | написал в поле ввода | «напомни Сергею про расчёт» |

### Куда человек пишет

Одно поле на всех страницах — правый столбец помощника, «Спросить или поставить задачу». Человек не выбирает категорию и не заполняет форму, он просто пишет словами.

Написанное разбирается на поля и возвращается карточкой, а не ответом в чате:

```
вы: напомни Сергею прислать расчёт по переплёту до четверга

    Задача · Сергей · четверг 14 ноя
    Напомнить про расчёт по переплёту
    основание: вы, 11 ноя 15:06
    [поставить]  [изменить]
```

Чего не хватает — показывается как видимый пробел, а не додумывается: «без исполнителя», «без срока». Эти пробелы уже есть в макете страницы «Задачи».

### Где задача появляется

- обратимая — сразу в списке «Поручения людям» или «Наблюдения»;
- необратимая или значимая — в полосе «Без вас не двинется» внизу экрана, и там же остаётся, пока человек не нажмёт.

### Данные задачи

```
{
  id, текст, владелец, срок, статус,
  основание: { тип: "протокол" | "правило" | "документ" | "наблюдение" | "человек",
               ссылка, цитата, дата },
  ключПовтора
}
```

Задача без основания не создаётся. `ключПовтора` обеспечивает требование безопасного повтора.

## Календарь: читаем, а не строим

У заказчика корпоративного календаря нет. Это не повод писать свой.

### Почему не писать свой

Календарь выглядит простым и им не является: повторяющиеся события, исключения из повторов, часовые пояса, приглашения и ответы участников, занят/свободен, напоминания, синхронизация с телефонами, разрешение конфликтов. Каждый пункт — недели работы.

И главное: календарь, которого не видно в телефоне, мёртв. Если руководитель в восемь утра не видит завтрашнюю встречу на своём телефоне, он ведёт расписание там, где видит, а наши данные протухают за неделю.

### Разделяем источник и страницу

| Слой | Чей | Что внутри |
|---|---|---|
| Источник встреч | чужой, подменяемый | дата, время, название, участники |
| Страница встреч | наш, наша система дизайна | повестка, собранный пакет, протокол, незакрытые поручения, предложения агента |

Второй слой — то, чего нет ни в одном календаре, и ради чего всё затевается. Первый слой за одним интерфейсом `getMeetings(период)`, реализации: CalDAV, Google, Microsoft, наш файл.

Соответствие системе дизайна обеспечивается тем, что наша страница — наша. Чужой календарь мы не перекрашиваем, мы из него только читаем даты.

### Варианты источника

1. **Microsoft 365 или Google Workspace** — если компания уже на одном из них, календарь оплачен и установлен, им просто не пользуются. Это самый дешёвый путь: не внедрение, а включение.
2. **Свой сервер CalDAV** — Nextcloud, SOGo, Radicale. Данные остаются у компании, протокол стандартный, синхронизация с телефонами работает из коробки. Подходит, если служба безопасности против облака.
3. **Наш файл** — только для демонстрации.

### На демонстрацию

Источник — наш файл со встречами. Час работы вместо месяца. Контракт `getMeetings` описан, mock повторяет его вместе с ошибками, переключение на живой календарь потом ничего не ломает.

## Роль ассистента

В штате 170 человек и есть ассистенты. Это значит, что систему каждый день водит не руководитель, а ассистент: он готовит, собирает, напоминает. Руководитель принимает решения.

Следствие для прав: нужна роль «ассистент» — видит очередь руководителя и может готовить всё, что в ней лежит, но подтверждение необратимого остаётся за руководителем либо выдаётся ассистенту явной делегацией на конкретный тип действия.

Это прямое попадание в требование слайда 09: роли ограничивают данные, действия и контекст AI. И это хорошо показывается на демонстрации — один и тот же экран под двумя ролями выглядит по-разному.

## Почта и мессенджеры

### Регламент чтения

Из каждого письма агент обязан вытащить фиксированный набор полей. Поле либо взято из письма, либо помечено как отсутствующее — третьего не дано.

- кто пишет, впервые или продолжение переписки
- что требуется: решение · ответ · информация · ничего
- срок, сумма, обязательство — если есть
- к чему относится: встреча · заказ · договор · задача
- чего не хватает, чтобы ответить

Из этого набора собирается карточка. Сортировка — не по важности (субъективно, доверие теряется), а по тому, что требуется от человека.

### Регламент черновика

- тон: как пишет сам руководитель, выведено из его прошлых писем
- длина: по умолчанию коротко
- никогда не вставлять суммы, сроки и обязательства, которых нет в исходных данных
- чего не знает — оставляет видимый пробел, а не правдоподобную подстановку
- обязательно указывает, на чём основан черновик

Регламент лежит файлом, который правит человек, а не кодом. После каждой правки прогоняются проверки, чтобы подкрученный тон не сломал запрет выдумывать.

### Три уровня отправки

| Что уходит | Условие | Кто нажимает |
|---|---|---|
| Готовый файл или фиксированная фраза | проверяемые условия, правило задал человек | уходит само, запись в журнал |
| Сочинённый черновик | любое письмо | человек, одно нажатие |
| Что угодно с числами, сроками, ценами, обязательствами | даже если правило совпало | человек, всегда |

Третья строка — предохранитель: правило совпало, но в ответе появилось число, значит правило не срабатывает и письмо уходит в очередь.

Граница простая: **автоответ допустим только когда ответ не сочиняется**. Как только модель пишет новый текст от имени руководителя, нужен человек.

### Режим наблюдения для правил

Новое правило неделю работает вхолостую и показывает, что оно бы отправило и на что. Человек проверяет список и только потом включает. Плюс ежедневная сводка ушедшего и кнопка «выключить» у каждого правила.

### Окно почты

Строим не входящие, а очередь: только письма, которые чего-то ждут от человека. Карточка, причина попадания, действие на месте. Полноценный почтовый клиент не делаем — он у них есть, а треды, вложения, поиск и несколько ящиков стоят месяцев.

### Telegram

Два применения, оба безопасные:

- **выход** — агент пишет руководителю в телефон: пакет собран, появился подходящий тендер;
- **вход** — руководитель пишет с телефона «напомни Сергею про расчёт», и это попадает в ту же очередь задач.

Бот через Bot API видит только адресованное ему. Чтение чатов и групп не делаем: это худшая поверхность для подложенных команд и самый шумный источник.

### Соцсети

Не подключаем. Для фотопечатной компании это входящие заявки клиентов — они принадлежат продажам и CRM, а не ассистенту руководителя. Исключение: конкретный канал, где регулярно появляется то, что решает лично руководитель — тогда это наблюдение за одним источником, та же механика, что с госзакупками.

## Роли и права — черновик

В бизнес-процессы заказчика нас не погружали, поэтому это предположение, а не факт. Роли и права лежат данными в `data/access.json`, а не в коде: исправить распределение — значит поменять файл, без разработчика. Демонстрация идёт от лица директора.

### Роли

| Роль | Кто это |
|---|---|
| `director` | директор |
| `deputy_growth` | заместитель директора по развитию |
| `deputy_tech` | заместитель директора по технологиям |
| `manager` | менеджер |
| `assistant` | ассистент, работает по поручению руководителя |

### Что видит каждая роль

Зоны: `production` — производство, оборудование, подрядчики; `commerce` — договоры, клиенты, прайсы, тендеры; `finance` — счета, оплаты, зарплаты.

| Роль | Зоны | Исключения |
|---|---|---|
| Директор | все | нет, видит всё |
| Зам по развитию | commerce, finance | не видит производственные регламенты и данные подрядчиков |
| Зам по технологиям | production, commerce | не видит финансы: счета, оплаты, зарплаты |
| Менеджер | production | только то, что нужно для работы: регламенты, график, прайс |
| Ассистент | production, commerce | не видит финансы; всё, что делает, помечается «по поручению» |

### Что может каждая роль

| Действие | Директор | Замы | Менеджер | Ассистент |
|---|---|---|---|---|
| Ставить задачу себе | да | да | да | да |
| Назначать задачу другому | да | в своей зоне | нет | готовит, не назначает |
| Подтверждать необратимое | да | в своей зоне, до порога | нет | нет |
| Менять правила агента | да | нет | нет | предлагает |
| Смотреть журнал | весь | свою зону | свои записи | зону руководителя |

Порог для замов задаётся суммой и типом действия: отправка письма внешнему контрагенту и назначение задачи внутри зоны — можно, обязательства свыше порога и всё, что выходит за зону, — уходит директору.

### Контекст модели — не отдельное право

В модель попадает ровно то, что видит текущая роль, потому что фильтр прав стоит до поиска. Отдельного списка «что можно показывать AI» нет и быть не должно: два списка рано или поздно разойдутся. Источник истины один — `canSee`.

Требование слайда 09 «роли ограничивают данные, действия и контекст AI» закрывается этим целиком, и это проверяется эвалом `assertNoLeak`.

## Поведение при отказе внешних сервисов

Требование слайда 09: ясные состояния и объяснимые ошибки.

### Три уровня отказа

| Что случилось | Что делает система |
|---|---|
| Временный сбой: таймаут, 429, 503 | повтор с нарастающей паузой, до трёх раз, молча |
| Поставщик недоступен | автоматическое переключение по цепочке: основная модель → локальная → заготовки |
| Модели нет вообще | система работает дальше; отключается только то, что требует понимания текста |

Без модели продолжают работать календарь, реестр задач, очередь подтверждений, журнал, поиск по словам. Перестают собираться протокол, черновики ответов и выжимки из документов.

### Почему данные не теряются

Работа устроена как очередь заданий на диске, а не как «нажал и ждёшь ответа». Запись встречи и расшифровка ложатся файлами до того, как к ним притронется модель. Если модель отвалилась на сборке протокола, задание остаётся в очереди со статусом «ждёт модель» и выполнится само, когда модель вернётся.

Повторять задание безопасно сколько угодно: у него есть ключ идемпотентности, второго протокола и второй задачи не появится. Это та же механика, что требование безопасного повтора.

### Что видит человек

Не бесконечный крутящийся индикатор, а честная строка: «протокол собирается, модель недоступна, повторю автоматически». Плюс отметка в журнале. Пользователь всегда знает, ждёт система или сдалась.

## Решения по интеграциям

| Что | Чем закрываем | Как |
|---|---|---|
| Календарь | Google Calendar | у заказчика Gmail, значит календарь уже есть и оплачен; читаем через API |
| Задачи | Bitrix24 | REST API; задачи создаются там после подтверждения, наша страница показывает их |
| Почта | Gmail | только чтение, сортировка, черновики |
| Уведомления и мобильный ввод | Telegram | бот, выход и вход |

На демонстрации все четыре идут через mock-сервисы с описанными ошибками, как разрешает слайд 09.
